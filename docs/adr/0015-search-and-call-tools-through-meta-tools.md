# Expose connection tools once, with explicit account selection

The Gateway MCP advertises each authorized connection operation once as `connection_namespace.tool_name`. Account-qualified direct exposure would duplicate every schema for every Account, while meta-tool-only discovery made clients inspect inventory and learn a second call contract before doing useful work. Direct tools include the upstream schema under `arguments` and accessible Account Namespaces under `account`, with display names and kinds in the description. Account selection is optional with one accessible Account, required with several, and absent for accountless connections. Internal Account IDs remain private routing details; agents use readable namespaces.

Shared Account Namespaces cannot overlap any Personal Account Namespace, including Accounts not currently visible together. This prevents later Group or connection access changes from introducing ambiguity. Different Users may reuse the same Personal namespace. Database namespace claims serialize competing writes and release a namespace when its final Account is removed; the existing indexes still enforce Shared and per-User uniqueness. Migration rejects legacy cross-kind collisions without renaming Accounts, and backfills claims for valid existing Accounts.

Keeping upstream parameters in a typed `arguments` object avoids collisions with gateway routing fields. Each nested upstream schema has its own schema resource identity so local JSON Schema references retain their scope. The connection catalog currently owns one schema per operation; Accounts choose credentials, not schema variants. Account-dependent catalogs would require a separate discovery/storage change before distinct variants could be exposed safely.

Upstream tool annotations are retained through discovery, storage, compatibility search, and direct exposure, including explicit false values. Missing annotations remain absent rather than being inferred from tool names; clients apply MCP defaults. Existing catalogs require Refresh tools after the annotations migration. CoStack's own search is read-only and closed-world because it reads the authorized stored catalog; generic call meta-tools retain conservative hints because their behavior depends on the selected tool.

Tool Policies can match a name/pattern or an annotation condition: Read-only, Destructive, or Open-world. Precedence is exact tool override, name pattern, annotation rule, then the `*` default; no match blocks. Among name patterns, more non-wildcard characters wins. Equal-precedence matches choose Block, then Require approval, then Allow. Destructive means `readOnlyHint` is not true and `destructiveHint` is not false. Open-world means `openWorldHint` is not false. Read-only requires explicit `readOnlyHint: true`. Thus missing annotations remain conservative, and read-only tools never match Destructive even when their destructive hint is true or absent.

The editor, snapshots, discovery, and execution use the same policy evaluator and the editor identifies the winning rule. Per-tool actions create exact overrides, or remove them when inherited rules already produce the requested action. The same annotation conditions work on CoStack's built-in tools using their own published annotations. Annotation rules deliberately trust upstream metadata; they do not independently verify behavior. Policy edits and refreshed annotations are re-evaluated on execution through the existing approval paths.

Every direct call rechecks accessible Accounts, Tool Policies, and availability, and routes using connection, Account, and operation identity. Direct discovery requires the built-in `search_tools` policy to be Allow. Execution obeys the built-in `call_tool` policy, or `call_tool_with_approval` for upstream approval-required tools using client-managed approval. Gateway-enforced approval uses elicitation; client-managed approval trusts the invoking client to obtain approval for the exact Account and arguments before invocation. Service Accounts cannot execute approval-required tools. These are the same forwarding, auditing, and approval paths used by compatibility meta-tools.

Search matches whitespace-separated query terms as case-insensitive substrings across the qualified tool name, connection display name, account display name, and description. Empty queries return the full authorized catalog. Searches of three terms or fewer require every term. For longer natural-language queries without an exact result, search progressively removes trailing terms but retains at least the first two, allowing task details after the service and operation without forcing a second call. Guidance therefore puts service and operation first and favors reuse of returned schemas.

The Gateway MCP retains `search_tools`, `call_tool`, and the approval-annotated `call_tool_with_approval` for compatibility. Search returns account-qualified tool names, schemas, and policy metadata; these results continue to use the call meta-tools. Direct tools need no preceding CoStack search.

Connection managers see a built-in CoStack entry first in MCP Connections. It has Tools configuration only, without Accounts or upstream transport settings. Its policies apply globally to the three meta-tools and default to Allow to preserve existing behavior. Blocked meta-tools are omitted from discovery and rejected on invocation. Require Approval uses a client-native gateway prompt; clients without elicitation support and Service Accounts cannot invoke those meta-tools. Upstream Tool Policies still apply independently.

Tool descriptions and server initialization instructions prefer direct tools and explain the Principal's Approval Method. The compatibility search description includes distinct connection display names from the Principal's authorized results when discovery is allowed. Block and Require Approval do not load or advertise the direct catalog. Client-specific tool search and model behavior still determine how efficiently these definitions reach the model; protocol tests alone do not establish fewer model calls.
