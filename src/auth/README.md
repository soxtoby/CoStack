# Authentication boundary

Better Auth owns browser credentials, SSO, sessions, OAuth clients, consent, and MCP access tokens. Its handler is mounted at `/api/auth/*`.

Production requires `BETTER_AUTH_SECRET`, `APPLICATION_URL`, `DATABASE_URL`, `BOOTSTRAP_TOKEN`, and `RECOVERY_TOKEN`. Local email/password registration is rejected in production. The bootstrap and recovery endpoints are `/api/setup/bootstrap` and `/api/setup/recovery`.

The application owns Groups, Capabilities, Principal suspension, and Pre-provisioned Access. SSO provisioning requires an explicitly verified email by default. An authorized SSO administrator may disable “Require verified email” on the provider to trust its reported email for matching prepared access; this does not mark the email verified. A new User must still have active Pre-provisioned Access. Matching access is bound to the immutable issuer and subject and prepared Group memberships are claimed before the callback finishes. Missing access and unverified email redirect to separate explanations on `/access-denied`, with a sign-out action. Provisioning runs on every SSO login so a previously rejected User can retry after the administrator resolves access.

The administration UI must call Better Auth's SSO and OAuth client APIs rather than adding parallel provider or client tables. The database permits one SSO provider. Service Account creation and MCP token validation belong with the MCP endpoint because they must create and validate Better Auth OAuth clients as one workflow. `loadAuthorization` is the authorization entry point for that work.

SSO configuration requires a same-origin request from a User authorized for `manage_sso`. `SsoConfiguration` validates the issuer as public HTTPS, resolves its host, and uses Better Auth's discovery and issuer-match validation before saving. Advertised endpoints may use other origins (for example, Entra's Microsoft Graph user-info endpoint); each must also be public HTTPS and resolve only to public addresses. Redirects are rejected by Better Auth. DNS checks do not pin the subsequent connection's address; deployments should enforce private-network egress restrictions as well.

Discovered origins are trusted only for the authorized internal save request. Sign-in and callback requests derive trust from the persisted issuer and endpoints, rechecking DNS. Other authentication requests do not gain provider trust. No provider-specific origin list is required. Updates rediscover and replace endpoints. Better Auth 1.7's update API cannot clear an optional user-info endpoint, so an update that removes one is rejected explicitly rather than retaining the old endpoint.

`0002_better_auth.sql` is generated by Better Auth 1.7.2 and committed for review. Regenerate it after an intentional Better Auth upgrade.
